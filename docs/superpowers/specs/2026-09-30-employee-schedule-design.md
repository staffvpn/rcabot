# СменаБот — график сотрудников по дням

Дата: 2026-09-30
Статус: approved by заказчик (в переписке), спека фиксирует принятые решения
Связана со спекой: `2026-09-25-smena-bot-design.md` — эта спека **отменяет** её §8 пункт «Редактирование расписания работы через бота» в части назначения людей на дни (общий недельный график точки §5/`schedule` не трогаем, см. §6 ниже).

## 1. Назначение

Сейчас крон считает, что *любой* активный сотрудник может открыть смену любой день — напоминания за 10 минут и проверка опоздания шлются всем активным сотрудникам каждый день, независимо от того, работают ли они сегодня. На практике это даёт ложный шум: зарегистрировали нового сотрудника в середине дня — ему тут же прилетает «Опоздание», хотя настоящая смена уже часы как открыта (воспроизведено в проде 2026-09-30: смена открыта в 8:23, ложные опоздания в 8:31/16:16/16:46 по мере регистрации новых сотрудников).

Причина — бот не знает, кто сегодня реально должен работать. Исправляем: админ ведёт график прямо в боте (кто, в какой день, с какого по какое время), крон таргетирует напоминания и проверку опозданий строго по этому графику.

Источник вдохновения — заказчик уже ведёт график в стороннем приложении SuperShift и прислал экспортированный PDF за сентябрь. Проверили: у SuperShift нет публичного API и нет надёжного формата для автоматического импорта (PDF — это рендер календаря, не структурированные данные, и в нём вперемешку люди/роли, не относящиеся к этой кассе). Автоимпорт не делаем — заказчик подтвердил, что график будет вестись вручную прямо в боте.

## 2. Масштаб

- Один активный сотрудник или несколько на один день (подтверждено заказчиком — бывают пересекающиеся/сменяющие друг друга смены).
- Одна запись графика = один сотрудник + одна дата + один интервал времени (начало–конец). Без разбивки одного сотрудника на два интервала в один день — такого в реальном графике заказчика (PDF) не встречалось; если понадобится, это отдельная доработка.
- График не блокирует OPEN/CLOSER — это только таргетинг уведомлений, не пропускной контроль (см. §5). Сотрудник, которого нет в сегодняшнем графике, всё равно может нажать OPEN (подменяет кого-то, форс-мажор) — бот не должен мешать реальной работе точки.
- Импорт из SuperShift — вне рамок (см. §1).

## 3. Модель данных (D1 / SQLite)

Новая таблица `schedule_assignments`:
- `id` — text primary key
- `employee_id` — references `employees(id)`
- `shift_date` — text, `"2026-09-30"`
- `start_time` — text, `"08:30"`
- `end_time` — text, `"14:30"`

Без уникального ограничения на `(employee_id, shift_date)` в БД — UI не даёт создать вторую запись на ту же пару при добавлении (см. §4), но уровень БД не обязан это принудительно проверять (YAGNI: нет сценария, где это нарушится в обход бота).

## 4. Админ-панель: `/admin → 📅 График`

Новый, седьмой раздел меню, тот же паттерн, что у остальных редакторов (список + 🗑 + ➕ Добавить + ✅ Готово):

- Открытие показывает ближайшие 14 дней вперёд с назначениями (дата, сотрудник, время), отсортировано по дате. Пустой список — «На ближайшие две недели график пуст.»
- 🗑 на строке — удаляет эту запись.
- ➕ Добавить — три шага сессией (как добавление инструкции): 
  1. «Введите дату (например, 30.09):» → парсится в `shift_date` текущего года; если такая дата в этом году уже прошла, берётся следующий год (не нужно вводить дни за много лет вперёд, а «30.09» в октябре должно значить следующий сентябрь, не прошедший). Нераспознанный формат — ошибка с примером, сессия не закрывается (тот же паттерн, что у `addFromText` в `listEditor.ts`).
  2. Инлайн-клавиатура с активными сотрудниками (как в чек-листах) → выбор `employee_id`.
  3. «Введите время (например, 08:30-14:30):» → парсится в `start_time`/`end_time`. Нераспознанный формат — та же ошибка-с-примером, что и для даты, без выхода из сессии.
  4. Если на эту дату у этого сотрудника уже есть запись — она заменяется (не дублируется), это и есть редактирование через админку по факту («добавили по новой» = поправили время).
- ✅ Готово — как везде, закрывает сессию и подчищает служебные сообщения (см. `ephemeral.ts`, уже работает для остальных разделов).

## 5. Крон: таргетинг по графику вместо «все активные сотрудники»

Сейчас (`cron-tick/run.ts`): перебирает `listEmployees().filter(active)`, создаёт смену на сегодня каждому, у кого её ещё нет, и проверяет `decideReminders` для каждого. Отдельная временная заплатка (добавлена 2026-09-30) глушит повторные опоздания, если у точки уже есть открытая/закрытая смена сегодня — эта заплатка убирается этой фичей, так как график решает задачу точнее и по существу.

Новая логика:
- В начале тика — `store.listScheduleAssignments(dateKey)`: все назначения на сегодня.
- Для каждого назначения — своя смена (`getShift`/`createShift` как сейчас), но `decideReminders` получает **время из самого назначения** (`start_time`/`end_time`), а не из общего `schedule` точки.
- Сотрудники без назначения на сегодня — смена не создаётся, никаких напоминаний/проверок опоздания. (Если такой сотрудник всё же нажмёт OPEN вручную — обычный флоу `handleOpenButton` создаст смену сам, вне крона, это не ломается.)
- Несколько назначений в один день — каждое проверяется независимо по своему времени; венюшный «один в тик» dedup (I1, `lateAlreadyNotifiedThisTick`) остаётся, но теперь это дедуп **на одно назначение**, а не глобальный по всей точке — если у двоих разные интервалы и оба опоздали к своему времени, это два разных события, оба должны дойти до админа.

## 6. Общий недельный график точки (`schedule`) — не трогаем

Таблица `schedule` (Пн-Пт 08:30-19:30 и т.д.) остаётся как есть, используется только для:
- времени контрольного X-отчёта (14:20, в рабочие по графику дни) — это не привязано к конкретному сотруднику;
- как дефолт, который можно предложить при вводе времени в шаге 3 §4 (необязательное удобство, не обязательно к реализации в первой версии).

## 7. Опоздание — возвращаем имя

Раз теперь известно, кто должен был выйти, сообщение админам снова содержит имя:
`🔴 Опоздание: {ФИО} не открыл(а) смену вовремя (по графику {start_time}).`
Это отменяет правку от 2026-09-30 (тогда имя убрали, потому что бот не знал, кто должен работать) — теперь знает.

## 8. Тестирование

- TDD как обычно: новые тесты на `store` (CRUD `schedule_assignments`), на `cron-tick/run.ts` (таргетинг по назначениям, несколько человек в день, отсутствие назначения — тишина), на новый admin-редактор графика.
- Ручная проверка в реальном боте: добавить назначение на сегодня/завтра через `/admin → График`, убедиться, что напоминание и опоздание приходят только по нему.

## 9. Вне рамок (не делаем)

- Импорт графика из SuperShift или любого стороннего приложения (нет API, см. §1).
- Принудительный запрет OPEN/CLOSER для сотрудников вне графика — график только таргетирует уведомления.
- Разбивка одного сотрудника на несколько интервалов в один день.
- Редактирование общего недельного графика точки (`schedule`) — как и раньше, правится в базе напрямую.
